# Release vois-app-webview-next

One release is three steps in a fixed order. Only the first one touches the repo.

```
bumpp --recursive  ->  tag push  ->  Release workflow (GitHub Release + zip)
```

`scripts/release.mjs` runs the whole thing; every step can also be run alone.

```sh
node .pi/skills/release/scripts/release.mjs --type minor          # the whole flow
node .pi/skills/release/scripts/release.mjs --type patch --dry-run # print the plan only
node .pi/skills/release/scripts/release.mjs --skip-bump --skip-watch
```

| flag                                             | meaning                                                                                                       |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `--type`                                         | `patch` (default), `minor`, `major`, `premajor`, `preminor`, `prepatch`, `prerelease`, or an explicit version |
| `--dry-run`                                      | print the plan; nothing is bumped or pushed                                                                   |
| `--skip-bump` / `--skip-watch`                   | run one part of the flow                                                                                      |
| `--no-push`                                      | bump and tag locally, do not push (no workflow)                                                               |
| `--allow-dirty`                                  | skip the clean-tree check                                                                                     |
| `--watch-timeout`                                | seconds to wait for the GitHub Release (default 300)                                                          |

## 1. Bump

`bumpp --recursive` bumps the root and every `apps/*` / `packages/*` package, commits `chore: release vX.Y.Z`, tags, and pushes. The tag push is what starts CI, so a release is never local-only unless `--no-push` is passed.

Rules that are not optional:

- Run it from the repo root on `main`, with a clean tree. `--allow-dirty` exists but the release commit would then carry unrelated files.
- Commit messages before the release must follow Conventional Commits; `changelogithub` groups them on the release page and drops `chore(release)` noise. A vague commit ("update") is what reviewers see.
- Never edit `version` fields by hand: bumpp writes all six packages, and a half-bumped workspace breaks the build.

## 2. Watch the GitHub Release

`.github/workflows/release.yml` runs on `v*` tags: it builds `apps/website` with the `VITE_APP_ID` / `VITE_APP_KEY` secrets, zips `dist` into `vois-app-webview-<tag>.zip`, and publishes the GitHub Release with `changelogithub@14`.

`release.mjs` finds the run by tag (`gh run list --workflow release.yml`), follows it with `gh run watch --exit-status`, then waits for `gh release view <tag>` to report a published release with assets. A failed workflow aborts the run.

Do this by hand only to re-run the tail of a release:

```sh
gh run list --workflow release.yml --limit 5
gh run watch <database-id> --exit-status
gh release view v0.12.0 --json url,assets,isDraft
```

## Repository facts worth not rediscovering

- Release flow without this skill: `pnpm release` = `bumpp --recursive`, then the tag push triggers `.github/workflows/release.yml`.
- The GitHub Release body is generated by `changelogithub@14` in CI. It is the release page; nothing else reuses that markdown.
- Version bumps are recursive: root, `apps/*`, `packages/*`. All of them move together; a workspace where only some moved will not build.
- `bumpp` pushes by default. `--no-push` in `release.mjs` is the only way to keep a release local, and it also disables the workflow wait.
- `changelogithub` runs inside the workflow, so the GitHub Release is created by CI, not by `release.mjs`. The script only observes it.
