# iOS runtime findings (2026-11-09)

Behavior observed by running VoisChat on a physical iPhone, not by reading an
archive. This is the runtime counterpart to the static
[5.0.3+1 reconnaissance](/native/ios/v5.0.3+1/readme) and is cited from the
[browser contract](/native/bridge-contract).

Times are the debug capture's local (CST) clock, from `receivedAt` epoch
milliseconds. The failing protocols do **not** return the contract's
`{type, errcode, errmsg, data}` envelope at all; `success`/`message` is the
shape this build sends. The pay probes ran in a second run the same day as
direct handler tests, so their evidence is terminal output rather than
`events.jsonl`; see `## Payment bridge`.

## Exact exchanges

The debug pipeline records `protocol` on the event and stores only the parsed
`data` payload, so the request/response excerpts below are payloads. The H5
request envelope around them is `{type, data, callbackName}`.

### `get-page-params` (14:18:35)

Request payloads:

```json
{"page":"/","params":["access-token"]}
{"page":"/","params":["theme","lang"]}
```

Response payload as recorded (the token value is replaced by the pipeline):

```json
{"errcode":0,"errmsg":"ok","data":{"login-id":"1541034","lang":"zh-CN","access-token":"[redacted]","theme":"light"}}
```

Facts worth carrying into implementation:

- `errmsg` is `"ok"`, not the contract's `""` for success.
- Missing keys: `device-type`, `pkg-name`, `wxpay-appid`, `pay-method`.

### `close-page` (14:29:03)

Request:

```json
{"type":"close-page","data":{}}
```

No reply is expected. The capture records the send at 14:29:03; the native page
closed.

### `get-permissions`, `get-location`, `write-clipboard`

Request payloads recorded by the capture:

```json
{"params":[]}
{"params":["location"]}
{}
{"text":"sim-use-poc"}
```

Reply for every one of them:

```json
{"success":false,"message":"Unknown action"}
```

The `write-clipboard` payload above is a direct
`window.webkit.messageHandlers.uniBridgeCall` test with a non-sensitive string.
It bypasses the H5 bridge wrapper, so it is not recorded in `events.jsonl`; its
reply came back through the test's own callback. The H5's earlier
`write-clipboard` calls are not used as evidence here because they predate this
session and cannot be attributed to the native shell.

Evidence times: `get-permissions` 14:45:53 and 14:46:08 (`[]`), 14:46:18
(`["location"]`); `get-location` 14:47:56; `write-clipboard` 14:48 (direct
handler test, terminal output, not in `events.jsonl`).

### Two-step evaluation (second run)

`Runtime.evaluate` with `awaitPromise: true` did not resolve a Promise on this
target. Use two evaluations instead. The first sends the bridge message and
stores the native reply on a `window` global through the test callback. The
second reads the global after a delay. `## Payment bridge` and
`.pi/skills/verify-vois-native` use this pattern for every delayed probe.

## Payment bridge

Probed in the second run, as direct `uniBridgeCall` handler tests through the
WebKit inspector. The evidence is terminal output. `events.jsonl` records only
sends that go through the H5 bridge wrapper, and these probes bypass it.

### `wechat-app-prepay`: not registered

Request:

```json
{"type":"wechat-app-prepay","data":{},"callbackName":"bridge_callback_pay_test"}
```

Reply, exactly:

```json
{"success":false,"message":"Unknown action"}
```

No `errcode` key, the same shape as the other unregistered actions above.
Plausible non-empty `data` fields answered identically. Ten alternative names
all returned the same reply: `wechat-app-pay`, `wechat-pay`, `wechat-prepay`,
`wxpay`, `wxpay-app-prepay`, `pay`, `app-prepay`, `wx-buy`, `ios-wechat-pay`,
`wechat-iap`.

### `ios-app-prepay`: registered, Apple IAP

Request:

```json
{"type":"ios-app-prepay","data":{},"callbackName":"bridge_callback_pay_test"}
```

Reply, exactly:

```json
{"data":{},"type":"ios-app-prepay","errcode":-1,"errmsg":"未找到产品"}
```

This handler answers the `{type, errcode, errmsg, data}` envelope and reports a
missing product, so it is the App Store (IAP) path, not WeChat. WeChat app pay
inside this build's WebView is not available.

### Pay page params

`get-page-params` asked for
`["device-type","pkg-name","wxpay-appid","pay-method","login-id","lang"]` and
answered:

```json
{"errcode":0,"errmsg":"ok","data":{"lang":"zh-CN","theme":"light","login-id":"1541034","access-token":"[redacted]"}}
```

5.0.6 supplies none of the four pay params. The H5 falls back to
`pay-method: "wechat"` and its own `pkg-name` / `wxpay-appid` defaults.

## Build 1.0.0 reinstall (same day, second run)

The device was later reinstalled with VoisChat **1.0.0** (`com.voistech.wechat`).
The WebKit target stayed available, so the same direct probes ran again.

`wechat-app-prepay` with `{}` answered the protocol envelope, not the 5.0.6
unknown-action shape:

```json
{"errcode":-1,"data":{"prepayId":"","wxpaycode":-1},"type":"wechat-app-prepay","errmsg":"微信支付发起失败，请检查微信设置或 Universal Link 配置"}
```

The handler exists and attempted to launch WeChat. A second probe with dummy
non-empty fields (`partnerid 1900000109`, `prepayid wx1234567890`,
`noncestr testnonce`, `timestamp 1700000000`, `sign TESTSIGN`) brought WeChat to
the foreground with **商户支付下单ID非法**. After returning to VoisChat, the H5
global stayed `pending`. The native pending callback is keyed by `prepayId`, and
a WeChat-side rejection before a `PayResp` does not match it. Treat that as an
unknown result, not as success, and bound the H5 wait.

The page-params probe on 1.0.0 returned the same four keys only
(`lang`, `theme`, `login-id`, `access-token`); `device-type`, `pkg-name`,
`wxpay-appid`, and `pay-method` are still missing. The H5 fallbacks apply.

`ios-app-prepay` was not retested on 1.0.0, so its state stays at the 5.0.6
Apple IAP result. The 1.0.0 native device detail was reached and also has no
缴费充值 or 流量卡充值记录 entry.

The H5 entry itself was driven in this build from the worktree DevServer on
3021 (`http://192.168.1.87:3021/#/devices/1631010`). 缴费充值 rendered at the
right of 型号. Clicking it sent `POST /v2/subuser/simcard-create-renew-order`
with `{iccid, pay_method: "wechat", pkg_name: "com.voistech.wechat"}`. The
backend answered `errcode 42012`, and the page showed 下单失败 with that
message. No `wechat-app-prepay` send occurred. Screenshot:
`apps/website/.tmp/verify/device-recharge/ios-1.0.0-order-failed.png`
(gitignored).

### New test device and cancel (2026-11-10)

The account gained a second device, `wl301010386256` (user_id 1683740, CF03,
ICCID ending 000874, expiry 2026-11-30, `recharge: true`). That card creates
an order for 2900 fen (流量卡续费一年) and opens the WeChat payment sheet.

The first three attempts, on the pre-fix build, were cancelled in WeChat. The
capture has three `wechat-app-prepay` sends and zero receives. The H5 stayed
on 支付中 for the full 120-second deadline, then showed 支付失败 with the
unknown-result message. The three orders remain status 0 / charge_status 0.

A native cancel fix was tested on a later 1.0.0 install. In that run the H5
paying modal disappeared and `payState` became `{ kind: "idle" }`, staying
idle past the 120-second deadline. The fix is being reverted, so the current
build does not return a cancel result and the website no longer handles one.
A cancelled payment stays on 支付中 until the 120-second deadline and then
shows the unknown-result failure. The paying modal's manual 关闭 only hides it.

The debug capture did not record the temporary fix's `wechat-app-prepay`
receive while the app was backgrounded, so the exact `wxpaycode` was never
captured.

A successful WeChat payment is still unverified. The new card can create
orders and open WeChat, but every attempt in this run was cancelled. The H5
success path and `pay-wechat-trade-success` remain untested.

The payment sheet opened with the H5's app-id fallback, so WeChat accepted the
prepay for this merchant. A completed payment is still needed to confirm the
full amount and order state.

The build does not expose its WeChat app id (`wxpay-appid` is absent from page
params), so the H5 falls back to the Android app's WeChat app id (redacted in
`docs/native/android/v5.0.4+504/page-params.md`). A real payment must confirm
the backend prepay is generated for the iOS app's WeChat app id; otherwise
WeChat rejects it.

## What this build is not

- Neither VoisChat 5.0.6 nor the 1.0.0 reinstall is in `docs/native/index.json`:
  there is no archived artifact, SHA-256, or static analysis behind these
  claims. Everything here is **runtime-observed**, and anything not listed
  stays unknown rather than inferred.
- iOS page params omit `device-type`, `pkg-name`, `wxpay-appid`, and
  `pay-method` on both builds. The H5 must not assume them on iOS.
- On 5.0.6, unsupported actions answer `{"success":false,"message":"Unknown action"}`,
  so an `errcode` check alone will not see the failure. Treat the missing
  envelope as the observed 5.0.6 behavior; do not silently normalize it into a
  contract success.
- On 5.0.6, WeChat app pay cannot run in the WebView: `wechat-app-prepay` is
  not registered and `ios-app-prepay` is Apple IAP (`## Payment bridge`). The
  1.0.0 reinstall registers `wechat-app-prepay`; a real payment is still
  unverified (`## Build 1.0.0 reinstall`).
